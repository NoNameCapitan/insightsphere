# Как выделить оркестратор: исследование, продукт и проверка спроса

> Статус на 28.09.2026 после внешнего разбора: историческая гипотеза, не текущий план реализации. Выпуск 0.6.1 замораживает новые функции до 10 реальных задач отбора заказов. Актуальный порядок: Orchestrator-Real-Pilot-RU.md; решения по замечаниям: Orchestrator-Audit-Response-RU.md. Прежние номера будущих выпусков ниже не являются действующим расписанием.

28.09.2026 · Выпуск 0.6.0 · План первых четырёх недель после начала реального пилота

## Решение

Предлагаемое позиционирование: **«Персональный исполнитель небольших заказов: понятный бриф, доказанный результат, прозрачные затраты и сохранённый опыт»**.

Первый рынок для проверки — фрилансеры и небольшие агентства, которые делают клиентам повторяющиеся отчёты и простую автоматизацию таблиц. Это рабочая гипотеза, а не найденная платёжеспособная аудитория. Начальная услуга: получить обезличенные CSV/таблицы, подготовить повторяемую сводку и инструкцию с контрольным примером. Такой результат легче проверить, чем обещание «создать любой продукт».

Не обещаем технологическую сингулярность, автоматический заработок или отсутствие аналогов. Оркестрация, бюджеты, память, тестирование и согласования уже есть на рынке. Потенциальное отличие — удобство целого пути небольшого заказа для одного владельца и измеримая стоимость принятого результата. Его ещё нужно подтвердить сравнением.

## Что показало исследование аналогов

Источники изучены 28 сентября 2026 года. Это ограниченное кабинетное исследование: четыре направления, публичные сообщения и документация. Интервью с клиентами и практический сравнительный запуск конкурентов не проводились. Существование жалобы не доказывает массовость проблемы или её неустранённость в текущей версии.

Источник [7] показывает требования к успешной работе, а не отсутствие функциональности. Ни для одного аналога не доказано, что соответствующая проблема полностью не решается.

## Какие решения интегрированы в 0.6

Новый раздел приложения **«Результат для клиента»** объединяет:

1. **Каталог исследуемых болей.** Четыре карточки с источником, уровнем уверенности и предлагаемым ответом. Сигнал не называется доказанным спросом.
2. **Реестр интервью и опыта пилотов.** Сегмент, псевдоним, источник/дата разговора, конкретная проблема, текущий обходной способ, оценка потерь времени и интерес к пилоту. Повтор идентичной записи блокируется. Псевдонимы и ответы вводит владелец; личность не проверяется.
3. **Версионный бриф.** Проблема, результат, исключённые работы, срок, плановая цена, бюджет, ставка времени владельца и 3–10 критериев. Изменение сохраняет новую версию с причиной. Валюта внутри проекта фиксирована.
4. **Пакет требований исполнителю.** Markdown-файл текущего брифа для ручной передачи в ChatGPT/Claude Code. Он не запускает разработку и не даёт разрешения на внешние действия.
5. **Приёмка с доказательствами.** По каждому критерию — вердикт и конкретное основание. Владелец записывает текст результата или его версию и ссылку. Новая версия брифа делает прежнюю приёмку неактуальной; последняя отрицательная проверка снимает текущий статус принятия.
6. **Стоимость результата.** Суммируются прямые затраты и минуты владельца по всем записанным попыткам и версиям, включая неудачные. Стоимость собственного труда рассчитывается по текущей ставке брифа. Неизвестная прямая стоимость делает итог неизвестным. Плановая цена минус затраты — плановый остаток, не выручка.

История входит в общий экспорт контекста. Существующий раздел «Досвід і клієнти» остаётся местом для утверждения урока или кандидата новой инструкции. Приёмка результата сама не меняет поведение агентов.

**Границы реализации:** подтверждение ручное, истинность доказательства автоматически не устанавливается. Хеш фиксирует введённый текст, не содержимое внешней ссылки. Бюджет нового раздела информационный — не блокирует расходы внешних сервисов. Затраты не импортируются автоматически из провайдеров; незаписанные расходы неизвестны. Неизменяемые записи не редактируются задним числом; исправление ошибочной записи и уточнение неизвестной стоимости потребуют отдельного механизма корректировок. Автоматическая рассылка, производство продукта, клиентская подпись и платежи не подключены.

## Пошаговый план

### Шаг 1. Выбрать один результат, день 1

Владелец выбирает один тип заказа: сводный отчёт из таблиц. Координатор фиксирует предложение: «На ваших обезличенных примерах настроим повторяемый отчёт, приложим контрольный расчёт и инструкцию». Не включаем медицинские решения или персональные данные пациентов в первый пилот.

В приложении: «Досвід і клієнти» → создать проект «Пилот: отчёт из таблиц». Затем «Результат для клиента» → выбрать проект → заполнить бриф. Критерии для примера: все строки входного набора обработаны; контрольные суммы совпадают; повторный запуск даёт тот же результат; инструкция воспроизводится клиентом; отсутствуют непредусмотренные внешние передачи данных.

**Выход:** один понятный оффер и границы. Если услугу нельзя объяснить одним предложением, сузить объём.

### Шаг 2. Сформировать карту наблюдений, дни 1–3

Дослідник собирает 20–30 релевантных сообщений из официальных форумов, GitHub Issues, публичных обсуждений и отзывов о четырёх аналогах. Запросы: `Paperclip token cost review`, `CrewAI memory setup issue`, `Relevance AI pricing learning curve`, `Devin unclear requirements review effort`.

Для каждой записи проверяет дату, версию, статус исправления и контекст; исключает дубли, рекламные публикации и пересказы без исходного источника. Сохраняет ссылку, краткую проблему и существующий обходной путь. Текущие четыре карточки — начальная выборка, а не выполнение цели 20–30.

В приложении: раскрыть «Записать интервью или сигнал» → выбрать «Публичная жалоба» → внести источник и наблюдение. Не копировать личные контактные данные без необходимости.

**Выход:** таблица повторяющихся проблем с источниками. Отдельно отметить «исправлено», «есть решение, но сложно», «неизвестно». Отсутствие функции в найденной документации не считать доказательством её отсутствия.

### Шаг 3. Сравнить существующий способ решения, дни 3–5

Для каждой из трёх наиболее частых проблем пройти документацию конкурента: настройка, лимиты, встроенные проверки, экспорт, возможности локального запуска. Составить карточку «как решают сейчас / какие шаги остаются у человека / что наш продукт сокращает».

**Выход:** три гипотезы преимущества, каждая с измерением. Например: сократить время согласования брифа; снизить минуты ручной проверки; уменьшить полную стоимость одного принятого отчёта. «У нас тоже есть память» преимуществом не считается.

### Шаг 4. Найти 10 собеседников, дни 4–7

Начать с собственных профессиональных контактов, знакомых фрилансеров, небольших агентств и людей, публично описавших подходящую проблему. Отобрать тех, у кого есть недавний реальный случай, а не только интерес к ИИ. Публикации и личные обращения — после согласования конкретного канала и текста владельцем; автоматическая массовая рассылка не нужна.

Черновик приглашения: «Изучаю, где подготовка клиентских отчётов через ИИ отнимает больше времени, чем экономит. Можно 15 минут обсудить ваш последний случай? Покупать ничего не предлагаю; хочу понять процесс и потери».

**Выход:** 10 разговоров с заметками, не 10 обещаний купить. Сейчас они ещё не проведены.

### Шаг 5. Провести одинаковое интервью

Сначала открытые вопросы о последнем случае: что хотели получить; чем пользовались; где остановились; сколько времени ушло; как проверяли; что пришлось переделывать; кто принимает решение; за что уже платили. Попросить обезличенный пример. Не спрашивать «нравится ли вам моя идея» как основной критерий.

Затем опросник с несколькими ответами: что мешало?

1. Долго настраивать.
2. Непредсказуемые расходы.
3. Агент делает не то, что требовалось.
4. Трудно проверить результат.
5. Требования меняются и теряются.
6. Повторяются старые ошибки.
7. Сложно передать результат клиенту.
8. Неясно, окупилась ли работа.

Записать ответы и фактический случай в реестр. Время потерь — оценка респондента, пока не замерено. Согласие на интервью не является согласием на коммерческие сообщения.

### Шаг 6. Выбрать одну боль, конец недели 1

Рабочий порог для решения: минимум 5 из 10 независимых собеседников описали схожую проблему за последний месяц, минимум 3 предоставили обезличенный пример, минимум 2 согласились на конкретный пилот. Это внутренние пороги небольшого исследования, не статистическое доказательство рынка.

Если порог не достигнут, сменить сегмент или формулировку боли. Не добавлять ещё десять универсальных функций. «Согласен на пилот» записывать отдельно от оплаты.

### Шаг 7. Выполнить три пилота, неделя 2

Для каждого клиента: отдельный проект → бриф → согласование результата и цены вне приложения → выполнение → проверка по каждому критерию → запись затрат и времени → обратная связь. Для технической работы пока использовать установленный Claude Code или ручную передачу в ChatGPT: автоматического исполнителя продуктов в этой сборке нет.

Регистрировать каждую попытку, включая неудачную. При дополнительном пожелании сначала создать новую версию брифа с причиной и согласовать новый объём. Проверять результат по фиксированной версии, а не по новым упрощённым критериям.

**Выход:** три проверяемых результата с историей; согласованный платный пилот полезнее общего «интересно». Реальную оплату подтверждать отдельно, не кнопкой приёмки.

### Шаг 8. Сравнить с исходным способом, неделя 3

Взять 5–10 новых сопоставимых задач, не использованных для настройки. Выполнить старым способом и новым процессом на одинаковом типе входа; учитывать настройку, исправления и проверку. Если модель и окружение разные — прямо зафиксировать ограничение сравнения.

Измерять: долю принятых результатов, время владельца, суммарные прямые расходы, число переделок и повторение ошибок. По возможности проверяющий не знает, каким способом получен результат. Не удалять неудачные задачи из отчёта.

**Рабочий критерий продолжения:** качество не хуже, критических дефектов нет, а медиана времени владельца или стоимости принятого результата ниже хотя бы на 20%. Это целевой порог, не уже измеренное преимущество. Для вывода об экономии должны быть известны расходы всех попыток.

### Шаг 9. Превратить опыт в проверяемые улучшения

После каждой попытки: «Досвід і клієнти» → связанная задача → отзыв по категориям → владелец проверяет текст → урок проекта либо кандидат общей инструкции. Для общего кандидата сохраняются независимый набор, сравнение и возможность отката. Клиентское предпочтение не переносить автоматически в чужой проект.

**Выход:** объяснимая цепочка «ошибка → изменение → проверка → результат». Если выигрыш не подтверждён, изменение не продвигать. Число сохранённых уроков не является метрикой качества.

### Шаг 10. Упаковать доказательство ценности, неделя 4

С разрешения клиента подготовить один обезличенный кейс: исходная проблема, входные данные, критерии, результат, время до/после, расходы, ограничения. Создать короткую демонстрацию процесса и пример готового отчёта. В рекламе использовать только измеренные цифры.

Текст позиционирования после проверки: «Помогаем [сегменту] получать [результат] с [измеренный выигрыш]. До начала фиксируем критерии, после — показываем доказательства и затраты». Значения в скобках заполняются реальными данными.

### Шаг 11. Подключать только нужную автономность

Очередность дальнейшей разработки: очередь с восстановлением → создание продукта в изоляции → автоматический импорт фактических затрат → корректировки учёта с журналом → клиентское подтверждение → один канал связи с разрешениями → платёжный провайдер в тестовом режиме.

Причина приоритета: сначала надёжно выполнять выбранный заказ, затем увеличивать число клиентов. Канал, отправка, цена, доступы, бюджет и публикация согласуются конкретным пакетом. Новые мощности не включаются лишь потому, что прошло несколько итераций.

### Шаг 12. Принять решение о масштабе

После первых пилотов: оставить услугу, если клиенты принимают результат и экономика подтверждена; сузить, если слишком много ручных исключений; сменить гипотезу, если проблема редкая или никто не готов оплачивать её решение. Автономность расширять по измеренным результатам, а не по количеству агентов.

Долгосрочно защищаемое преимущество — собственный набор законно полученных обезличенных случаев, критериев приёмки, проверенных процедур и доверие конкретного сегмента. Сейчас такого накопленного преимущества ещё нет.

## Что делать прямо сейчас

1. Сделать резервную копию остановленной базы и распаковать 0.6 в отдельную папку.
2. Запустить диагностику, затем приложение подходящим Windows/Mac-запускачом.
3. Создать проект и заполнить первый бриф в «Результат для клиента».
4. Скачать пакет требований и выполнить одну пробную задачу на собственных обезличенных данных.
5. Записать реальную проверку, минуты работы и известные затраты. Если цифра неизвестна, оставить стоимость пустой.
6. Провести первое интервью по вопросам выше. Реестр готов, но система ещё не ищет респондентов и не пишет им сама.
