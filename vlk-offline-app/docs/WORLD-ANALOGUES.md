# Світові аналоги та обрана архітектура

Огляд систем, які розв'язують ту саму задачу — медична робота там, де на
інтернет покладатися не можна, — і пояснення, що з їхніх рішень узято
в цьому застосунку, а що свідомо не взято.

## Група A. Офлайн-first із синхронізацією на пристрої

| Система                                                                                                      | Що це                                         | Як працює офлайн                                                                                                                     |
| ------------------------------------------------------------------------------------------------------------ | --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| [Community Health Toolkit (Medic)](https://docs.communityhealthtoolkit.org/technical-overview/architecture/) | Платформа для громадських медпрацівників      | PouchDB у браузері/телефоні, двобічна реплікація до CouchDB; часткова реплікація — пристрій отримує лише свою підмножину документів  |
| [DHIS2 Android Capture](https://dhis2.org/android/)                                                          | Збір медичної статистики та трекінг пацієнтів | Метадані й дані зберігаються в локальній БД пристрою; вся валідація і правила працюють без мережі, синхронізація — при появі зв'язку |
| [CommCare (Dimagi)](https://github.com/dimagi/commcare-android)                                              | Форми для польових працівників                | Форми зберігаються локально й надсилаються автоматично; незавершені форми взагалі не залишають пристрій                              |
| [Bahmni Connect](https://bahmni.atlassian.net/wiki/spaces/BAH/pages/39813212/Bahmni+Connect+Features)        | Офлайн-клієнт EMR Bahmni / OpenMRS            | Локальна копія даних на клієнті, синхронізація з сервером лікарні                                                                    |
| [HospitalRun](https://hospitalrun.io/)                                                                       | EHR для лікарень у місцях із поганим зв'язком | Офлайн-first на PouchDB/CouchDB                                                                                                      |

Спільна риса: **дані живуть на пристрої працівника**, а центральний сервер —
це точка зведення. Ціна такого підходу — конфлікти версій, часткова
реплікація за правами доступу і медичні дані в сховищі браузера чи телефона.

## Група B. Локальний сервер установи

| Система                                                             | Модель розгортання                                        |
| ------------------------------------------------------------------- | --------------------------------------------------------- |
| [OpenMRS](https://openmrs.org/) / [Bahmni](https://www.bahmni.org/) | Сервер у лікарні, кабінети працюють через локальну мережу |
| [OpenEMR](https://www.open-emr.org/)                                | Класичний локальний сервер установи                       |
| [GNU Health](https://www.gnuhealth.org/)                            | Локальний сервер, робочі місця в LAN                      |

Це найближчий аналог до ВЛК Offline / Standby: одна установа, один сервер,
постійний диск, робота без зовнішніх сервісів.

## Група C. Пакування локального застосунку

| Підхід                                                                                                                                    | Суть                                                                                                           |
| ----------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| [Nesktop](https://github.com/nicnocquee/nesktop)                                                                                          | Next.js як локальний «настільний» застосунок без Electron: production-збірка піднімається на localhost         |
| Electron / Tauri                                                                                                                          | Браузерний рушій у комплекті; більший пакет, власний цикл оновлень                                             |
| [Air-gapped deployment](https://semaphore.io/blog/air-gapped-deployments-how-to-deploy-to-servers-without-internet-access-complete-guide) | Самодостатній артефакт збирається там, де є мережа, і переноситься носієм; перевірка SHA-256 після перенесення |

## Що взято в цей застосунок

1. **Модель групи B — сервер установи.** Комісія працює в одному приміщенні,
   писар один, паперовий підсумок теж один. Один SQLite на сервері дає
   транзакції, тригери незмінності підтверджених записів і єдиний журнал
   аудиту. Це робить конфлікти реплікації непотрібними.
2. **Пакування в дусі групи C.** Замість Electron — локальний Node-сервер і
   штатний браузер: менший пакет, без власного рушія оновлень, друк і PDF
   засобами системи.
3. **Практика air-gapped-розгортання.** `npm run pack:offline` збирає
   самодостатній архів із уже встановленими залежностями і готовою збіркою,
   з контрольною сумою SHA-256 і маніфестом платформи. Цільовий комп'ютер
   не звертається до реєстру пакетів жодного разу.
4. **Ідея «оболонка має відкриватися завжди» з групи A** — але лише для
   оболонки: service worker кешує статичні файли інтерфейсу і сторінку
   `/offline`, а також дає встановлення у вигляді окремого вікна.

## Що свідомо не взято

1. **Реплікація медичних даних у браузер (PouchDB / IndexedDB).**
   У групі A пристрій належить одному працівнику. Тут кабінетний комп'ютер
   спільний, і копія карток у сховищі браузера створила б витік, який
   неможливо контролювати засобами установи. Тому кеш містить лише
   знеособлені файли інтерфейсу, а `/api`, HTML-сторінки та потоки RSC
   не кешуються ніколи. Це перевіряє автоматичний тест.
2. **Автозбереження чернеток у браузері.** З тієї ж причини. Замість нього —
   явне попередження про втрату зв'язку, блокування закриття вкладки з
   незбереженою формою і збереження тексту на екрані до повторного надсилання.
3. **CRDT і автоматичне злиття (ElectricSQL, RxDB, Automerge).**
   Записувач один — сервер установи. Конкурентні зміни розв'язуються
   перевіркою версії запису з явним повідомленням працівникові, а не
   автоматичним злиттям медичного тексту.
4. **Автоматична синхронізація з МІС.** Підтвердженого API для перенесення
   немає, тому реалізовано керований ручний буфер з журналом звірки,
   а не «інтеграцію», яку неможливо перевірити.

## Межі порівняння

Наведені системи вирішують ширші задачі (багатоклінічні мережі, мобільні
бригади, національна статистика) і сертифіковані інакше. Порівняння стосується
лише моделі автономності, а не функціональної повноти чи нормативного статусу.
Цей застосунок — резервний режим роботи ВЛК на час недоступності МІС.
