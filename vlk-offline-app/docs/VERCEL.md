# Розгортання на Vercel

> **Спочатку головне.** Цей застосунок спроєктовано як локальний сервер
> установи: медичні дані лежать на її диску й не залишають будівлю.
> Розгортання на Vercel — це **інший режим роботи**: база переїжджає до
> хмарного провайдера, а автономність втрачається повністю. Рішення про
> обробку персональних медичних даних у зовнішній хмарі приймає установа,
> а не розробник. Для реальної роботи ВЛК передбачений локальний режим
> (`docs/OFFLINE.md`); хмарний режим доречний для демонстрації, перевірки
> інтерфейсу та навчання на вигаданих даних.

## Чому просте розгортання не працює

Vercel виконує застосунок у тимчасових екземплярах без постійного диска.
Файл `data/vlk.sqlite` зникав би разом з екземпляром, а паралельні екземпляри
бачили б різні копії бази. Тому застосунок **свідомо зупиняється**, якщо
виявляє Vercel і файловий `DATABASE_URL`:

```
На Vercel немає постійного диска. Задайте DATABASE_URL=libsql://… і DATABASE_AUTH_TOKEN
```

Розв'язання — винести базу в мережеву SQLite-сумісну службу
(libSQL / Turso). Схема, міграції та тригери незмінності залишаються ті самі.

## Крок 1. Створіть базу libSQL

Підійде будь-який провайдер libSQL; найпростіше — Turso:

```sh
turso db create vlk-standby
turso db show vlk-standby --url          # libsql://vlk-standby-<org>.turso.io
turso db tokens create vlk-standby       # токен доступу
```

Токен нікуди не вписуйте у код — лише у змінні оточення.

## Крок 2. Застосуйте міграції та створіть адміністратора

З комп'ютера, де є цей проєкт (не з Vercel — там немає інтерактивного вводу):

```sh
npm ci
export DATABASE_URL="libsql://vlk-standby-<org>.turso.io"
export DATABASE_AUTH_TOKEN="<токен>"

npm run db:generate
npm run db:migrate:remote   # міграції у віддалену базу libSQL
npm run setup               # перший адміністратор і довідник МКХ
```

`npm run db:migrate` робить те саме, самостійно обираючи рушій за
`DATABASE_URL`; `db:migrate:remote` викликає віддалений рушій напряму.
Формат таблиці `_prisma_migrations` і контрольні суми sha256 однакові для
обох рушіїв, тому `prisma migrate status` бачить однаковий стан схеми.

`setup` не створює `.env` у віддаленому режимі — налаштування задаються
змінними оточення Vercel.

## Крок 3. Змінні оточення проєкту Vercel

```sh
vercel env add DATABASE_URL production        # libsql://vlk-standby-<org>.turso.io
vercel env add DATABASE_AUTH_TOKEN production # токен Turso
vercel env add APP_ORIGIN production          # https://<проєкт>.vercel.app
vercel env add ALLOWED_ORIGINS production     # https://<проєкт>.vercel.app
vercel env add COOKIE_SECURE production       # true
```

Те саме можна зробити у вебінтерфейсі: **Settings → Environment Variables**.

| Змінна                    | Значення                              |
| ------------------------- | ------------------------------------- |
| `DATABASE_URL`            | `libsql://vlk-standby-<org>.turso.io` |
| `DATABASE_AUTH_TOKEN`     | токен Turso                           |
| `APP_ORIGIN`              | `https://<ваш-проєкт>.vercel.app`     |
| `ALLOWED_ORIGINS`         | `https://<ваш-проєкт>.vercel.app`     |
| `COOKIE_SECURE`           | `true`                                |
| `COMMISSION_NAME`         | назва комісії                         |
| `ORDER_402_REVISION`      | реквізити чинної редакції             |
| `NEXT_TELEMETRY_DISABLED` | `1`                                   |

`APP_ORIGIN` і `ALLOWED_ORIGINS` мають точно збігатися з адресою в браузері,
без завершального `/`. Інакше збереження форми поверне
«Адреса доступу не дозволена»: це навмисна перевірка походження запиту.

Кожне попереднє розгортання (preview) має власний домен — додайте його в
`ALLOWED_ORIGINS` або користуйтеся лише production-адресою.

> **Vercel не підхоплює змінні оточення на льоту.** Після додавання або зміни
> будь-якої з них потрібне повторне розгортання: `vercel --prod` або кнопка
> **Redeploy** у вебінтерфейсі. Доти працюватиме попередня конфігурація.

## Якщо змінних ще немає

Збірка на Vercel **не падає** без бази: клієнт бази не створюється під час
імпорту модуля, тому `next build` проходить і без `DATABASE_URL`.
Застосунок при цьому не віддає 500 — усі сторінки показують екран очікування
з причиною, а `/api/health` називає її машинно:

```sh
curl https://<проєкт>.vercel.app/api/health
{"status":"misconfigured","driver":null,"detail":"Не задано DATABASE_URL…"}
```

Отже, порядок вільний: можна спершу розгорнути, потім додати змінні
оточення й повторити розгортання. Сторінка `/offline` доступна завжди,
бо не звертається до бази.

## Крок 4. Розгортання

```sh
vercel --prod
```

Або підключіть репозиторій у вебінтерфейсі Vercel. `vercel.json` уже задає
фреймворк, команди встановлення та збірки. Під час збірки на Vercel
`output: "standalone"` вимикається автоматично — пакує платформа.

Після розгортання перевірте стан:

```sh
curl https://<проєкт>.vercel.app/api/health
```

| Відповідь                                 | Що означає                                           |
| ----------------------------------------- | ---------------------------------------------------- |
| `200 {"status":"ok","driver":"remote",…}` | усе працює                                           |
| `503 {"status":"misconfigured",…}`        | немає `DATABASE_URL` / `DATABASE_AUTH_TOKEN`         |
| `503 {"status":"unreachable",…}`          | змінні є, але база не відповідає або токен недійсний |
| `503 {"status":"migrations-pending",…}`   | з'єднання є, але таблиць немає — виконайте крок 2    |

Сторінки при цьому **не падають у 500**: замість кабінету показується екран
очікування з тією самою причиною і кроками для виправлення.

## Що працює і що не працює в хмарному режимі

| Можливість                                      | Стан у хмарі                                                                           |
| ----------------------------------------------- | -------------------------------------------------------------------------------------- |
| Реєстрація, огляди, підсумок, ролі, аудит       | Працює                                                                                 |
| Друк талона та зведення, PDF браузером          | Працює                                                                                 |
| Буфер ручного перенесення в МІС                 | Працює                                                                                 |
| Експорт JSON / CSV / XLSX                       | Працює                                                                                 |
| Сторінка `/offline` і кеш оболонки              | Працює                                                                                 |
| **Робота без інтернету**                        | **Ні**                                                                                 |
| `npm run backup` / `npm run restore`            | Ні — розраховані на локальний файл; користуйтеся резервним копіюванням провайдера бази |
| `npm run offline:check`, `npm run pack:offline` | Ні — стосуються локального режиму                                                      |
| Зберігання даних у межах установи               | Ні                                                                                     |

## Повернення до локального режиму

Нічого перебудовувати не потрібно: достатньо `DATABASE_URL=file:…`.
Обидва режими живуть в одному пакеті й визначаються лише цією змінною.

## Обмеження перевірки

Шлях Prisma → `@prisma/adapter-libsql` перевірено на справжній схемі ВЛК:
міграції, створення записів, читання, 14 таблиць і 16 тригерів незмінності,
а також запуск сервера Next.js з цим адаптером (`/api/health`, `/login`).
Окремо відтворено збірку без жодних змінних оточення — саме так виглядає
перше розгортання проєкту Vercel.
Саме розгортання на Vercel і мережевий транспорт до Turso в середовищі
розробки не перевірялися — потрібні облікові записи обох служб.
