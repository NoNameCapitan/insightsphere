# v1.9 — публікація, ліди, тарифи, модератори

Реалізовано три блоки, які перетворюють VetNear з «каталогу з даними в білді»
на продукт із серверним джерелом правди та вимірюваною комерційною метрикою.

---

## 1. Supabase як source of truth публічного фіду

**Проблема до v1.9.** Схвалення заявки в серверній черзі модерації ставило
статус `approved` — і на цьому все закінчувалося. Заклад ніколи не потрапляв
до публічного списку. У roadmap це було записано як «production next step».

**Що зроблено.**

| Компонент | Роль |
|---|---|
| `published_places` (міграція 002) | таблиця опублікованих закладів; повний `Place` JSON у `data` |
| `src/lib/places/publish.ts` | чистий мапер `submissionToPlace()` + `mergePlaceLayers()` |
| `src/lib/server/placesFeed.ts` | серверне читання з fallback на seed |
| `GET /api/places/published` | публічний ендпойнт, кеш 60 с |
| `src/lib/store.ts` → `hydratePublishedPlaces()` | клієнтське злиття seed + DB |
| `POST /api/admin/submissions` | схвалення → upsert у `published_places` |

**Інваріанти маперу (покриті тестами).**

1. `emergencyAvailable` і `isOpen24_7` **ніколи** не публікуються з даних
   партнера. Розблоковує їх лише зафіксований дзвінок
   (`phoneConfirmedAt` + `phoneConfirmedBy`).
2. Заклад без валідних координат публікується як `needs_geocoding` і
   автоматично випадає з пошуку та мапи через наявний
   `isSearchablePublicPlace()`.
3. Координати поза межами Києва відхиляються — одна помилка в цифрі не має
   ставити маркер у полі.
4. `verified: false`, доки людина не перевірила. Заявка партнера — це
   provenance `partner_submitted`, а не верифікація.
5. Відхилення або призупинення заявки знімає заклад із публікації.

**Політика відмов.** Помилка бази ніколи не залишає сайт порожнім:
`getPublishedPlaces()` логує і повертає лише seed-шар. Некоректний рядок
пропускається через `isPlaceLike()`, а не рендериться.

## 2. Ліди — метрика, за яку платить партнер

`POST /api/events/lead` записує вихідну дію на картці: `call`, `route`,
`website`, `social`, `request`, `detail_view`.

**Приватність за замовчуванням.** Не зберігаються ні IP, ні user-agent, ні
ідентифікатор користувача. `session_hash` — це SHA-256 від
`день + сіль + client key`, обрізаний до 32 символів. Він стабільний у межах
доби (щоб не рахувати один дабл-тап як два ліди) і **змінюється щодня**, тому
відстежити людину між днями ним неможливо. Унікальний індекс
`(place_id, event_type, session_hash, created_at::date)` робить дедуплікацію
на рівні БД.

**Оплачувані vs неоплачувані.** `BILLABLE_LEAD_TYPES = [call, route, request]`.
Перегляд картки лідом не вважається — це принципово, інакше рахунок партнера
роздувається переглядами.

**Читання:** `GET /api/partner/leads?placeId=&days=30` повертає щільний ряд по
днях (без пропусків, які легко неправильно прочитати на графіку) плюс
`billableLeads`. UI — `/admin/leads`.

Клієнт відправляє подію через `navigator.sendBeacon`, бо `tel:` і посилання на
карти зазвичай скасовують звичайний `fetch`.

## 3. Комерційні тарифи без втрати чесності даних

`free` → `verified` → `promoted`. Платний лише `promoted`.

Правила зафіксовані в `src/lib/places/tier.ts` і покриті тестами:

- промо — це **тайбрейкер** (`-1.2` до скору), а не перевизначення сортування:
  ближчий на кілька кілометрів заклад лишається вище;
- промо **завжди** має видиму мітку «Промо» на картці;
- промо **повністю вимкнене** в терміновому режимі — гроші не змінюють порядок
  невідкладної допомоги;
- промо без дати завершення відхиляється ендпойнтом (`promotedDays` 1..365);
  прострочене промо тихо деградує до органічної позиції.

Тариф `verified` не дає жодної переваги в ранжуванні — він лише відображає
підтвердження і не є способом купити позицію.

## 4. Модератори замість спільного ADMIN_TOKEN

`moderator_tokens` зберігає лише SHA-256 дайджест. Плейнтекст показується один
раз під час випуску.

```bash
node scripts/moderator-token.mjs issue "Ірина (модератор)" moderator
node scripts/moderator-token.mjs list
node scripts/moderator-token.mjs revoke mod_xxx
```

Що це дає порівняно зі спільним секретом: **відкликання** (без ротації секрету
для всіх), **атрибуцію** (`moderation_events.actor_id`) і **розділення ролей**
(зміна тарифу вимагає `admin`). `ADMIN_TOKEN` лишається як bootstrap-шлях, щоб
наявний деплой не зламався, поки випускаються справжні токени.

Supabase Auth залишається наступним кроком — для партнерських кабінетів, де
потрібні сесії та self-service.

## Змінні середовища, додані у v1.9

| Змінна | Обовʼязкова | Призначення |
|---|---|---|
| `LEAD_HASH_SALT` | ні (рекомендовано) | сіль для денного хешу сесії; без неї береться префікс service-role ключа |

Решта — без змін: без Supabase застосунок працює в демо-режимі, `/api/events/lead`
відповідає `204` і нічого не пише, `/api/places/published` повертає порожній список.

## Перевірено локально

| Команда | Результат |
|---|---|
| `npm run lint` | чисто |
| `npx tsc --noEmit` | чисто |
| `npm test` | 149/149 (було 109) |
| `npm run build` | ✓ compiled, 24/24 сторінки |

**Межа перевірки.** Усі чисті модулі (мапер, ліди, тарифи, ранжування) покриті
юніт-тестами. Маршрути API проти справжнього Supabase тут **не** виконувалися —
потрібен проєкт із застосованою міграцією 002. Порядок розгортання:
міграція → `LEAD_HASH_SALT` → випуск токена → схвалення тестової заявки →
перевірка, що заклад зʼявився у `/nearby`.
