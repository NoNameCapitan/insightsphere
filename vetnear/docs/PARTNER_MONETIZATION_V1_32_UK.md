# Партнерська програма VetNear: підготовка монетизації v1.32

Стан на 17 листопада 2026 року. Підготовлено код і сценарій обговорення партнерства. Платіжного провайдера не підключено, гроші не стягуються, підписки не активуються. Заявка на ранній пілот не є договором або обіцянкою купівлі.

## Що працює в цій версії

- `/for-partners`: безкоштовний профіль після модерації, майбутні інструменти, запропоновані ціни та зрозумілий перехід до обговорення.
- `/partner-interest?plan=pro&founding=1`: форма із закладом, населеним пунктом, робочим email, побажаннями, обраним планом та окремою згодою на розгляд заявки. Позначка раннього партнера означає готовність дати зворотний звʼязок; вона не надає знижки чи пріоритету.
- Без `NEXT_PUBLIC_BACKEND_ENABLED=1` форма зберігає тільки локальну чернетку й прямо повідомляє, що команда нічого не отримала. Чернетка містить контактні дані; її можна видалити очищенням даних сайту. Після відновлення згоду потрібно дати знову.
- З підключеним сервером `POST /api/partner-interest` приймає тільки дозволені поля, примусово ставить `pending_review` і повертає `paymentStatus: unpaid`, `planActive: false`. Помилка або тайм-аут не показують успіх. Тайм-аут може настати після запису в базу, тому повтор незмінених даних використовує той самий UUID; `upsert` з `ignoreDuplicates` не створює другу заявку та не перезаписує першу. Зміна змісту створює нову заявку. Це не глобальне усунення повторів за email.
- Серверна черга доступна через `GET /api/admin/partner-interest?page=0`: лише чинний персональний токен модератора, по 50 записів, відповідь `no-store`. У v1.32 це API для оператора; окремий екран опрацювання заявок, автоматичні листи та зміна статусів у UI ще не реалізовані.
- `/partner/dashboard` показує локальні заявки. Вигадані конверсії й числові результати прибрано. Кабінет не є серверною партнерською авторизацією й не підтверджує публікацію або оплату.
- `POST /api/admin/places/tier` відмовляє в новій активації будь-якого платного рівня, доки провайдер вимкнений. Повернення до безкоштовного рівня збережено.

## Ціни: пропозиції, а не затверджені тарифи

Збережено попередні продуктові орієнтири. Не створено жодного платіжного price ID, checkout або рахунку.

| План у UI | Внутрішній ID | Пропозиція на місяць | Стан |
| --- | --- | --- | --- |
| Базовий | `free` | Безкоштовно | Профіль після модерації |
| Партнер | `verified` | 449 ₴ | Ціна не затверджена, інструменти заплановані |
| Партнер Pro | `pro` | 1 349 ₴ | Ціна не затверджена, інструменти заплановані |
| Мережа | `multi_location` | Від 2 699 ₴ | Ціна не затверджена, склад філій обговорюється |

`verified` збережено як технічний ID для сумісності. Назва для користувача — «Партнер». Оплата не підтверджує клінічну компетентність, види тварин, графік, телефонну перевірку або прийом 24/7. Платні пропозиції мають `priceApproved: false`. Немає обіцянки кількості звернень, продажів, SLA, відсотка пожертв або гарантованої позиції.

## Межа платних можливостей

Чистий модуль `src/lib/billing/entitlements.ts` готує правила для майбутнього серверного підключення. Поки провайдер вимкнений, результат завжди базовий. Цей модуль сам не доводить факт оплати: довірений сервер у майбутньому має зібрати стан після перевіреного webhook, а не з localStorage, URL чи клієнтського JSON.

| Стан | Розширений профіль / аналітика | Кілька філій | Промо |
| --- | --- | --- | --- |
| Локальна чернетка або отримана заявка | Ні | Ні | Ні |
| Провайдер вимкнений; pending, unpaid, past_due, cancelled або refunded | Ні | Ні | Ні |
| Майбутній підтверджений активний «Партнер» | Так | Ні | Ні |
| Майбутній підтверджений активний Pro | Так | Ні | Лише звичайний пошук |
| Майбутня підтверджена активна «Мережа» | Так | Так | Лише звичайний пошук |

Для майбутнього активного стану потрібні затверджений price ID, ID підписки, ID перевіреної події, дата оплати та чинний оплачений період. Відсутні/некоректні дати, майбутня оплата або завершений період закривають платні можливості. За термінового пошуку промо вимикається. `verificationBadge` і `emergencyBadge` завжди `false`; платний профіль без промо також не отримує legacy tier `verified`.

Старий `Place.tier` і `promotedUntil` залишаються сумісними полями комерційного показу. Вони не є доказом оплати. Нова модель підписки ще не підʼєднана до читання профілів/партнерського акаунта й не перевіряє історичні записи автоматично. Перед увімкненням реальних платежів треба звірити й мігрувати наявні tier-записи; прямі записи в БД не замінюють платіжного процесу.

## База та конфігурація

Новий файл `supabase/migrations/005_partner_plan_requests.sql` підготовлено, але в реальній БД у межах цієї роботи не виконано. Для нового середовища послідовність — `001`–`005`, далі `006_geography_optional_district.sql` для заявок поза районами Києва. Для наявного середовища застосовують тільки ще не виконані міграції, спочатку на staging.

Міграція 005 створює:

1. `partner_plan_requests`: заявка, версія згоди, `pending_review`; UUID є ключем повтору.
2. `partner_billing_events`: місце для майбутньої дедуплікації подій провайдера; без сирих карткових даних і повних webhook payloads.
3. `partner_billing_subscriptions`: майбутній стан оплати, періоду та посилання на подію. CHECK для `active` вимагає paid і явні NOT NULL для обох меж періоду.

Таблиці мають RLS і відкликані права `anon` / `authenticated`. Публічних політик немає. Міграція не додає активних підписок. Сам зовнішній ключ на подію ще не гарантує `signature_verified`: перевірка підпису й атомарне застосування події залишаються обовʼязковою частиною майбутнього довіреного сервера.

Для серверного приймання потрібні наявні `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_BACKEND_ENABLED=1`, а для production — `LEAD_HASH_SALT`, `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` і решта вимог `npm run release:gate`. Секрети тільки на сервері. Нових billing env у цій версії немає: змінна середовища сама по собі не може ввімкнути оплату. Для черги використовують особистий токен модератора, не спільний `ADMIN_TOKEN`.

Публічний endpoint обмежує тіло 8 192 байт і спроби 5 за 10 хвилин. В email/логах не друкуються тіло заявки й контактні дані. Автоматичні email-повідомлення, передача даних CRM та зовнішній billing відсутні. Строк зберігання заявок і процедура їх видалення мають бути затверджені оператором до широкого збору; автоматичного очищення саме цих нових таблиць ще немає.

## Що потрібно до реальних платежів

1. Затвердити юридичну особу продавця, валюту, ціни, податкові документи, оферту/договір, скасування, повернення й обробку персональних даних. Підтвердити доступність обраного провайдера для цієї особи та України; бренд провайдера наперед не зафіксовано.
2. Реалізувати партнерський вхід, перевірку права керувати закладом/філіями та серверне розмежування доступу. Поточний локальний кабінет цього не забезпечує.
3. Замінити тільки вимкнений адаптер у `src/lib/billing/provider.ts` на провайдера в sandbox. Створювати checkout сервером за затвердженим price ID; не приймати суму/статус paid від браузера.
4. Додати webhook із перевіркою підпису по сирому тілу, захистом від повторного відтворення, дедуплікацією event ID, транзакційним записом події/підписки та звіркою з провайдером. Обробити дублікати, порушення порядку подій, затримки, прострочення, refund і chargeback. Сам редирект «успішна оплата» не активує послугу.
5. Підʼєднати entitlements до серверного читання функцій, звірити legacy tiers, додати реальні звіти з правами на власний заклад. Називати натискання телефону натисканням: воно не доводить розмову чи візит. Історичний `billableLeads` — внутрішня класифікація дій, а не підстава автоматичного рахунку.
6. Перевірити staging-платіж, відмову, retry, скасування, повернення, контроль прав, відсутність платного впливу в urgent, видиму позначку промо та фактичну роботу узгоджених інструментів. Лише після цього окремо дозволити production-провайдера й оновити публічні умови.

## Перевірка цієї зміни

Цільовий набір: 50/50 тестів у `partnerMonetization.test.ts`, `partnerInterestApi.test.ts`, `leads.test.ts`, з них 26 нових. Перевірено відмову без провайдера, pending/unpaid/refunded, необхідні докази й дати, urgent без промо, відсутність медичних значків, неактивний адаптер, очищення інʼєкцій платіжних полів та чесну серверну квитанцію/помилку. `npx tsc --noEmit` і ESLint змінених TypeScript-файлів пройшли. Інтеграційний запис у живий Supabase, застосування міграцій і справжній checkout не виконувалися. Повний релізний verify та браузерні результати зберігаються у загальному звіті v1.32.

Чернетки першого контакту — у [PARTNER_OUTREACH_DRAFTS_UK.md](PARTNER_OUTREACH_DRAFTS_UK.md). Жодного контакту не здійснено.
